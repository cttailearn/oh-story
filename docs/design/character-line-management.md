# 角色线（人物变化）管理与规划方案 —— 面向 AI 写作

> 目的：回答「小说中角色的变化（角色线）一般怎么处理」；说明 oh-story 当前的处理方式及其上限；
> 给出 4 套可用于 AI 写作的替代/增强方案，并配套「角色卡 + 角色线」的具体规划模板。
> 适用读者：需要让 LLM 连续写完几十到几百万字、且要求「人设不崩、弧线可见、伏笔可查」的作者与 dev。
> 参考文献列于文末；凡标「观测」的经验点，均来自本仓库现有实现与你所在社区的工具实践。

---

## 0. TL;DR（一分钟结论）

- **角色线 = 人物在故事里的变化轨迹**。它不是「剧情线」（发生了什么），而是「角色因此如何改变 / 不变」（信念、能力、身份、关系、情绪）。
- 业界成熟理论（K.M. Weiland）把弧线分为**正弧/平弧/负弧**，用**「角色相信的谎言」vs「真相」、Want vs Need、创伤 Ghost** 来定义起点与终点。
- AI 写长篇的核心难题不是「写不出变化」，而是**「变化」与「一致」之间的平衡 + 无长期记忆 + 变化证据不可重建**。
- oh-story 当前做法：**角色线 = 角色卡内的「阶段规划」（计划）+ 追踪/角色状态快照（事实）**，靠机械校验保证一致。它已解决「计划/事实混淆」和「上下文可控」，但对「线的整体节奏、渐变证据、多线交织、内在信念维度」「弧线审计」支撑偏弱。
- **4 套方案**（可组合）：
  - 方案 A：**弧线文件独立** + 阶段状态机（线为中心）——治「一条线看不出全貌」
  - 方案 B：**状态事实库**（时间戳 + 图谱，JSON/SQLite）——治「渐变证据与审计」
  - 方案 C：**触发式知识库 + 近况卡 + 摘要记忆**（lorebook 思路）——治「上下文成本与会话遗忘」
  - 方案 D：**写后记账代理 + 弧线审计闸门**（流程为中心）——治「说了不算，写了才算」
- 推荐：当前仓库先以 **A + D** 增量落地（成本低、与现有 agent 体系对齐），再视规模接入 **B** 的事实库与 **C** 的触发注入。

## 1. 角色线是什么：人物变化的三层结构

可以把任何一个角色的「线」拆成三层，每层都有独立的推进节奏：

| 层 | 内容 | 典型变化 | 弧线理论对应 |
| --- | --- | --- | --- |
| 内在层 | 信念 / 价值 / 欲望 / 恐惧 / 弱点 | 畏惧信任 → 敢于依赖；复仇执念 → 放下 | Lie→Truth、Want→Need（Weiland） |
| 外在层 | 能力 / 身份 / 地位 / 资源 / 外形 | 学徒 → 宗师；弃妇 → 女帝 | 能力成长、身份逆袭 |
| 关系层 | 与其它角色的距离 / 信任 / 敌友 | 陌生 → 恋人；师徒 → 决裂 | 关系弧（NovelCrafter/AIFiction 均有关系模块） |

**关键心法：角色线 ≠ 剧情线。** 剧情线回答「发生了什么」，角色线回答「角色因此变成什么样」。AI 默认的写作模式是「每章 event-driven 重写」，如果不在工程上把这两者分开，
LLM 会写出「剧情在走、人物没变」或「人物突然大变、像换了个人」——这分别是扁平化与崩人设，是 AI 长篇最大的两个死因。

## 2. 为什么 AI 写作必须「专门」处理角色线（难点盘点）

1. **无长期记忆**：LLM 上下文窗口有限（通常数万 token）。写到第 80 章它不记得第 3 章主角说过什么——这是所有 AI 长篇工具（马良、webnovel-writer、AIFiction 等）一致承认的根因与主战场。
2. **一致性 vs 变化的物理张力**：既要「维持人设稳定」（不崩），又要「显示成长」（不平）。AI 容易走极端：要么每章行为一致 = 无成长；要么一次事件就剧变 = 人设崩。需要「渐变的增量证据」来约束。
3. **渐变不可见**：人物变化是逐步累积的。若只记录「当前值」、不记「每一步从哪变到哪」，弧线无法检查、无法回放、无法在后期补救。
4. **多角色 × 多线并行**：主角、女主、配角、反派各有弧线，还互相交织（感情线、势力线、伏笔线）。以角色为索引的文件体系，查「一条线」要横跨多个文件。
5. **可验证性**：靠 LLM「感觉」检查一致性不可靠。需要能被机械校验（grep/脚本/固定字段）的东西：事实锚点、阶段编号、伏笔状态、证据所在章节。
6. **成本**：把全部设定塞进 prompt 又贵又会爆炸。必须「按需注入 + 固定读取量不随章数增长」。

oh-story 的前置判断与以上一致，且把 1/5/6 解决得不错；缺口主要在 2/3/4。

## 3. 当前 oh-story 的处理方式（基线，先看清再谈改进）

### 3.1 一句话概括当前模型

> **角色线 = 拆分到「角色卡」内的阶段规划（计划态） + 「追踪/角色状态」快照（事实态）；两者用「机械校验」衔接；正文写完后由事务机制落盘。**

### 3.2 落盘结构（v2.x，pi/dsh 双运行时）

```text
{书名}/
├── 设定/
│   ├── 角色/{角色名}.md        ← 角色卡：静态事实 + 设计蓝图 + 「角色线」计划
│   └── 关系.md                 ← 全局关系映射（一个文件一张网）
├── 大纲/
│   ├── 卷纲/第X卷.md           ← 卷级节奏（含各线/阶段的分布与高低潮）
│   └── 细纲/第XXX章.md         ← 每章蓝图（含「关系变化」「阶段位置」字段）
├── 正文/第XXX章_*.md
└── 追踪/                       ← 唯一结构化权威 + 派生视图
    ├── _tracking-state.json    ← 事务状态（fail-closed）
    ├── 上下文.md               ← 续写状态卡（固定 7 栏，≤12KB）
    ├── 角色状态/{角色名}.md    ← 当前快照（身份/位置/目标/身心/能力资源/关系/已知/未结）
    ├── 伏笔.md                 ← 派生伏笔视图
    └── 时间线/（作者真相.md / 读者已知.md）
```

### 3.3 「角色线」在角色卡里长什么样（现有契约）

角色卡是**6 大标题制**，其中第 5 个标题就是「角色线」：

```markdown
# 角色卡：沈栀（女主）

## 基础信息     # 字段格式：`字段名：结论（补充描述）`，括号前结论供 checker 机械比对
## 形象与能力   # 分时期表 + 能力上限（跨时期永久形态事实留卡，临时状态归追踪）
## 说话方式     # 对话音色唯一权威，禁止临场发挥
## 角色线
> 只写计划；实际进度以 追踪/ 与卷纲为准。
### 阶段 1：面包店初遇（第一卷·第1-8章）
- 阶段目标：陌生人 → 认识
- 关键事件与场景：…
- 同场角色：…
- 解锁/伏笔：…（埋【袖口颜料】伏笔，阶段 3 回收）
- 阶段情绪：戒备 → 微暖
### 阶段 2：…（结构同上，随剧情增量补写）
### 与其他线交织点
- 第一卷：与主角线交汇（本线高潮与主线错峰）
### 当前进度指针
→ 以 大纲/卷纲/第X卷.md 与 追踪/ 为准
## 写作红线     # 绝不做的事/性格漂移禁区（consistency-checker 逐条 grep）
## 本书专属
```

### 3.4 支撑机制

- **静态/动态边界**：角色卡只写"不变事实 + 计划"；位置/当前目标/身心状态/关系现状一律归 `追踪/角色状态/`。两处不写同一状态，避免自相矛盾。
- **事实锚点格式**：`字段名：结论（补充）`——consistency-checker 第零步取括号前结论值做机械比对；散文/表格会让机械核对失效。
- **阶段编号连续性**：`### 阶段 N` 必须从 1 连续编号，checker 机械校验，中途插入则整体重排。
- **每章事务**：`tracking_commit.py` 读事务 JSON（含 `character_changes` + `character_snapshots`），整份覆盖核心角色小快照，不追加历史；`check` 缺状态即 fail-closed 停写。
- **上下文注入**：`story-explorer` 的 `context_load` 固定读取量不随章数增长——细纲提到谁就带谁的卡 + 该角色状态快照。
- **反推**：`story-import` 用 `character-state-reverse.md` 从已写正文反推快照（只取截至最后完整章的当前值，不造历史）。

### 3.5 这张图的优点与缺口

| 优点 | 缺口（本次要解决的方向） |
| --- | --- |
| 计划（卡）与事实（追踪）分离，防「计划被当成已发生」 | 角色线是**卡的下属段落**，不是一等对象 → 单看「一条线」要翻整张卡，节奏/高低潮不可视化 |
| 事实锚点 + 脚本 = 可机械校验 | 快照只记**当前值**，不记**变化序列** → 渐变不可重建，「为什么变成这样」要翻逐章记录 |
| 8 栏固定快照 + 固定读取量 = 上下文可控 | 8 栏偏**外在维度**（身份/位置/目标/能力/关系），**内在信念/欲望/弱点的动态**没有专属维度 → 内在弧线最容易丢 |
| 每章事务 + fail-closed = 不写坏账 | 阶段推进靠「指针 + 手工同步」，**无自动弧线推进/审计** → 计划被写飞了没人拦 |
| story-explorer 查询体系完整 | 关系只有一张静态图，**关系弧的「时间线」**没有独立视图 |

## 4. 四个方案（含角色卡与角色线如何规划，方便 AI 写作）

四个方案分别以 **线 / 数据 / 上下文 / 流程** 为中心，互不冲突，可任意组合。每个方案都给出：
①一句话定位 ②核心机制 ③角色卡如何规划 ④角色线如何规划（含模板与示例） ⑤如何接入 oh-story ⑥优缺点与适用场景。

---

## 方案 A：弧线独立成文 ——「角色线文件 + 阶段状态机」（线为中心）

### 4A.1 一句话定位

把「角色线」从角色卡里**拆出来成为独立文件**，并给每条线加一个**可推进、可校验的阶段状态机**，让「一条线」成为可整体查看、整体推进、整体检查的一等对象。

### 4A.2 核心机制

- 每个核心角色 / 每条主线（感情线、师徒线、复仇线）一个文件：`大纲/角色线/{角色名或线名}.md`。
- 文件结构 = **线头（不变的目标/类型）+ 阶段数组（带状态）+ 交织点 + 进度指针**，其中阶段是状态机的状态：
  - 每个阶段记录：`状态: planned | active | done`、`章节范围`、`进入条件`（由哪条细纲/事件触发）、`验收信号`（读者可见的改变，最好是可 grep 的句子/动作）、`证据锚点`（完成后回填：`第N章 段落号/语句`）、`影响维度`（内在/外在/关系）。
- **只允许按序推进**：`tracking_commit` 增加 `arc_advance` 动作——写完一章后判断本线是否应推进；跳到未激活阶段或缺少证据锚点即报错（fail-closed，同现有 check 语义）。
- 角色卡保留静态与「线锚」，「角色线」标题退化为一行指针：`→ 追踪线全文见 大纲/角色线/{线名}.md；当前姿态：{一句话}`。

### 4A.3 角色卡如何规划（与现在几乎兼容）

- 角色卡 6 大标题全保留，仅「角色线」标题改为**指针 + 当前姿态一句话**（每次推进由记账机制回写姿态，卡不自说自话）。
- 新增一行「弧线定义」放线头：`弧线类型：正弧/平弧/负弧（Weiland 五类）`；`起点信念（Lie/Want/弱点）→ 终点信念（Truth/Need）`。
- 这样角色卡仍然回答「这是个什么样的人 + 他不变的红线」，而「他如何变」交给线文件。

```markdown
# 角色卡：沈栀（女主）
## 基础信息   ## 形象与能力   ## 说话方式
## 角色线
- 弧线类型：正弧（自我价值觉醒）
- 起点（第1卷）：相信「自己只能是负担」（Lie）→ 需求是「被需要是有价值的」（Truth/Need）
- 终点（第4卷）：接受帮助、主动求助
- 线文件：大纲/角色线/沈栀.md  当前姿态：阶段1·戒备→微暖（已过第8章）
## 写作红线   ## 本书专属
```

### 4A.4 角色线如何规划（线文件模板）

```markdown
# 角色线：沈栀（女主·自我价值觉醒）   ← 线文件用 H1 + 定位括号

## 弧线定义
- 类型：正弧（Positive Change Arc）
- Lie（角色相信的谎言）：我只会拖累别人
- Truth（故事要教会的真相）：允许被需要，也是力量
- Want（表层所求）：考上美院（Lie 驱动） / Need（深层需要）：学会求助（Truth 驱动）
- Ghost（创伤来源）：单亲、母亲三份工供她学画，被「懂事」驯化
- 关键证据维度：求助行为 / 拒绝施舍的次数 / 与主角的距离

## 阶段状态机
### 阶段 1：戒备→微暖（第1-8章）[状态: done]
- 进入条件：面包店相遇事件（细纲第1章）
- 变化信号：不再拒绝主角顺手扶门；主动递回落下的话
- 证据锚点：第7章「……也行吧（小声）谢了。」
- 维度：关系层
### 阶段 2：…（第9-30章）[状态: active]
- 进入条件：美术联考危机
- 变化信号：第一次主动开口向主角求助（哪怕一句）
- 证据锚点：（完成后回填）
### 阶段 3：…（第X卷）[状态: planned]

## 与其他线交织点
- 第1卷与主角主线交汇（面包店）；本线高潮第X卷与主线错峰
## 进度指针
- 最近推进：第8章（由 arc_advance 记账）
```

> AI 写作友好点：每次写章前，`context_load` 只带「当前阶段」这一段（含进入条件与变化信号），长度固定；写完由记账动作推进状态并回填证据。整条线的节奏一眼可见，可算「每阶段距起点/终点还差几步」。

### 4A.5 接入 oh-story

- 目录：新建 `大纲/角色线/` 放线文件；角色卡「角色线」标题改指针（保留向后兼容：短期可两处并行）。
- 机制：`tracking_commit.py` 增加弧线推进；`consistency-checker` 增加「线文件阶段编号连续性 + 证据锚点存在性」两项机械检查（沿用现有 grep/字段校验基建）。
- 拆文侧：`story-import` 的 `character-state-reverse.md` 增加「按已写正文初始化线文件阶段状态」，从此项目反向获得完整弧线。

### 4A.6 优缺点

- 优点：①一条线整体可看、可检查、可回放；②与细纲/卷纲解耦（阶段边界 = 事件边界，不强绑章节号）；③在现有「卡+追踪」架构上改动最小、纯 Markdown 可落地；④弧线理论（Lie/Truth）直接进模板，中后期审查有据。
- 缺点：①线文件需维护，与卷纲双向同步有手工成本；②「进入条件」若写得不像事件会发生错位推进；③对「一个角色多条线」要拆分得够干净。

## 方案 B：状态事实库 ——「时间戳 + 知识图谱」统一管理（数据为中心）

### 4B.1 一句话定位

把「角色当前状态」从**整份覆盖的快照**升级为**带时间戳的增量事实库**（每维度的值 + `since 第N章` + `证据`），可选接 SQLite / 知识图谱，从根上解决「渐变证据」与「跨角色多线审计」。

### 4B.2 核心机制

- 每个角色一条 record，维度 = 既有 8 栏 + 新增**内在维度**（信念/欲望/恐惧/弱点/对外姿态）。每个维度存一个**值 + 时间戳 + 出处**：
  ```json
  { "维度": "belief_selfworth",
    "history": [
      {"since": 1, "value": "我不配", "evidence": "第1章向妈妈道歉段"},
      {"since": 37, "value": "也许我能行", "evidence": "第37章联考报名"},
      {"since": 120, "value": "被需要是力量", "evidence": "第120章主动求助"}
    ]}
  ```
- **追加式 delta**：变化 = 在该维度追加一条带时间戳的记录；替换现在的「整份覆盖快照」。旧值永不丢失 → 渐变可重建、可回放、可审计。
- **派生三重视图（视图不是存储，随查随算）**：
  1. 当前视图（= 各维度最新值）→ 注入写作上下文；
  2. 弧线视图（= 某维度值随章节的变化列表）→ 该角色「变化的证据链」；
  3. 关系时间线（= 关系边上带状态的变更列表）→ 感情/势力线进度。
- **图谱可选增强**：实体（角色/物品/地点/秘密）+ 带状态的关系边 + 伏笔（带状态的实体属性）。写前注入「本节相关子图」；写后更新子图。参考马良/NovelForge/AIFiction 的「知识图谱 + 记忆中枢」做法。

### 4B.3 角色卡如何规划

- 角色卡 = **事实 schema 宣言 + 静态信息 + 线目标**：声明「本书要追踪哪些维度」（默认内在 + 外在 + 关系，可加减），并把每个维度的**起点值 → 终点值 → 途经章节**作为「维度目标规划表」写进线头：

```markdown
## 角色卡：沈栀（女主）
## 追踪维度（schema）
- belief_selfworth（自我价值）    目标：我不配 → 被需要是力量（第1→4卷）
- ability_art（绘画）             目标：省前百 → 校考名额（第1→2卷）
- relation_mc（与主角距离）       目标：戒备 → 深恋（第1→4卷，阶段化）
（其余 8 栏默认自动追踪）
```

### 4B.4 角色线如何规划

- 角色线 = **维度目标规划表 + 检查规则**，不用再手写一长串事件，因为「变化」被显式拆到维度上：

```markdown
# 角色线：沈栀
## 维度目标
| 维度 | 起点(since) | 终点 | 途经阶段章节 | 检查规则 |
| --- | --- | --- | --- | --- |
| belief_selfworth | 我不配(1) | 被需要是力量 | 每卷至少一次标记 | 越级(1→120 一步到位)报错 |
| relation_mc | 戒备(1) | 深恋 | 第1卷:认识;第2卷:依赖;第3卷:暧昧;第4卷:定情 | 每阶段必须有一次 evidence |
## 关键事件钩（可选，触发维度变化的标志事件）
- 第1章面包店 = belief 初始化的契机
- 第37章联考报名 = belief 第1次上移
```

- **审计（每卷一次，自动化）**：对每一维度检查「实际值序列 vs 目标序列」——提前量/滞后量、是否越级、缺证据点；输出偏差报告驱动修订。即「设定审计」（马良）在角色线层面的落地。

### 4B.5 接入 oh-story

- 最小版：仍用文件系统，把 `追踪/角色状态/{角色名}.md` 从「覆盖式快照」改为「带时间戳的多维度记录」（Markdown 表格即可），`tracking_commit.py` 由覆盖改为追加 + 校验连续性。
- 进阶版：SQLite 一张 `character_dims` 表 + 一张 `relation_edges` 表；`context_load` 直接查库，`story-explorer` 加 `arc_progress` / `dim_history` 查询类型。
- 图谱版：接 `设定/关系.md` 升级为带状态/时间的关系边文件，供多线交织查询（“第5-10章间所有关系恶化的对”之类）。

### 4B.6 优缺点

- 优点：①渐变证据永久可重建，「为什么变成这样」一句话查到；②维度化之后**内在弧线不再丢**；③审计（计划 vs 实际）可完全自动化，防「写飞」；④多角色多线用图/表查询极高效，天然支持大规模。
- 缺点：①工程量大（schema/DB/工具链），纯 Markdown 场景偏重；②过度结构化有僵化创意的风险——需保留「即兴变化」的入口（允许 > 计划的新 evidence，触发再规划）；③模型输出要严格服从 schema，需要强校验。

## 方案 C：触发式知识库 + 近况卡 + 摘要记忆（上下文为中心，lorebook 思路）

### 4C.1 一句话定位

借鉴 SillyTavern 的角色卡/世界书（lorebook）与摘要记忆机制：把每个角色的信息按「常驻 / 触发 / 按需」分层，按章节关键词**只注入活跃角色**；用递归摘要持续压缩已写内容，让「长期记忆」以固定 token 维持——这是上下文成本最低的方案。

### 4C.2 核心机制

- **分层条目**（每个角色对应一组条目）：
  - L0 常驻（constant，永远进 prompt）：名字、一句话人设、核心红线、当前线外姿态。
  - L1 触发（selective，关键词命中才进）：详细人设 / 说话方式 7 维 / 完整关系。
  - L2 按需（用户或查询才取）：背景故事、家世、历史行为的详细记忆。
- **世界书 / lorebook**：条目带 `keys`（触发词，如角色名/代号/tag）、`constant`（是否常驻）、`insertion_order`。SillyTavern 的 World Info 就是这套（见文末链接）。
- **近况卡（scene/beat 摘要）**：每条写过的章节压缩为「该线近 3 次状态变化」的一句话级摘要（递归摘要，不全文保留）。这与 oh-story 的 `追踪/上下文.md`（近三章速记）同构，可平滑升级。
- **弧线总览**：每条线一个 ≤ 数 KB 的总览（阶段 + 当前姿态），替代“翻整张卡”。

### 4C.3 角色卡如何规划

把角色卡拆成**一个「人设卡」+ 若干「条目」**：

```markdown
# 人设卡：沈栀
## L0 常驻（每次写入）
- 身份：班长、深夜面包店兼职、单亲；外柔内韧，嘴硬心软
- 红线：不主动求助/不收施舍；绝不说「我爱你」
## L1 触发（命中最频繁，角色在场时注入）
- keys: 沈栀 | 栀 | 面包店
- 说话方式7维 / 外貌记忆点 / 与主角当前关系一句话
## L2 按需
- 家世细节 / 童年创伤原文 / 历史行为全记录
```

### 4C.4 角色线如何规划

- **角色线 = 「近况卡 + 弧线总览」双件套**，代替长篇阶段枚举：
  - 近况卡：`截至第N章，沈栀与主角：认识（第1-8章戒备→微暖）；能力：省前百；信念：不敢求助（未变）…`——每次写后由摘要记账重写，始终 ≤ 500 字。
  - 弧线总览：`阶段1(1-8章)达成√ → 阶段2(9-30章)进行中。下阶段变化信号：第一次主动求助。`
- 说明：L1 触发词覆盖**角色名 + 主要 tag** 即可；久别回归时，靠 L2 + 近况卡完整恢复「她是谁 + 她最近怎样」，正好解决「小师妹第 60 章回归谁还记得她」的问题（马良也在强调这点的必要性）。

### 4C.5 接入 oh-story

- 直接把现有「角色卡 6 标题 + 角色状态 8 栏」映射到 L0/L1/L2：常驻 = 基础信息划线部分；触发 = 详细卡；按需 = 历史。
- `story-explorer.context_load` 增加**触发匹配**：细纲出现角色名 → 注入 L0 + L1；`追踪/上下文.md` 升级为「近 5 章摘要 + 各活跃线近况卡」（从 7 栏到 7+X 栏，控制 ≤ 12KB）。
- 摘要记账：`author_memory_commit.py` 除了现有内容，再产出「本线近况」的更新（一句话改写机制）。

### 4C.6 优缺点

- 优点：①上下文成本最低、实现最接近 LLM 原生能力、上手快；②天然解决「配角久别回归」与「会话中断恢复」；③与现有上下文卡（本节速记/近况卡）结构同构，兼容平滑。
- 缺点：①触发词漏配 = 该角色信息静默丢失（需要 fallback：没命中时仍带 L0）；②摘要压缩有失真风险（细节被模型改写）；③一致性主要靠 prompt 而非机械校验 → 必须叠加「验证钩子」（方案 D 的审计）兜底。

## 方案 D：写后记账代理 + 弧线审计闸门（流程为中心）

### 4D.1 一句话定位

把「角色线管理」从「靠作者自觉 / 靠卡里写计划」变成流水线里的**显式工序**：写前装上下文 → 写后**记账代理**增量结账（谁变了、从哪到哪、证据在哪章、弧线推进到哪）→ **审计闸门**定期校验（计划 vs 实际、提前/滞后、缺证据），不合格就不准继续。

### 4D.2 核心机制

- **角色线 = 可执行检查单（契约式阶段）**：每个阶段明确「本阶段结束读者应看到什么」（验收信号），并给出**可机器定位的证据**（某句式/某动作/某字段），让审计有据可依——这正是 oh-story 现有「基础信息事实锚点」思想向「弧线」的推广。
- **写后记账代理**（即 oh-story 的 `chapter-extractor` 多一个职责，或独立 `arc-bookkeeper`）：
  1. 读本章正文 → 产出 `character_changes: [{who, dimension, from, to, evidence_chapter, evidence_snippet}]`；
  2. 判定线推进：`arc_advance: {line, stage, from, to, ok: bool}`（只允许按序推进）；
  3. 交给 `tracking_commit` 落盘并 `check`（fail-closed）。
- **弧线审计闸门**（consistency-checker 扩展，每卷或每 10-20 章跑一次）：
  - 计划节奏 vs 实际节奏（该进阶段 N 却还停在 N-2 → 滞后告警；跳过 N 直升 N+1 → 越级告警）；
  - 证据缺失清单（阶段标记 done 但无证据锚点 → 报错）；
  - 全维度/全角色扫描（借用方案 B 的结构，或纯 grep）。
  - 输出偏差报告 → 驱动「回炉修订」或「调整后续大纲」（与 马良「设定审计」、oh-story 的 `story-review` 对齐）。

### 4D.3 角色卡如何规划

- 角色卡 = 静态 + 红线（同现状），新增**「验收标准」小节**（可 grep 契约）：

```markdown
## 角色线（契约式）
### 阶段 1：戒备→微暖（第1-8章）  [验收：读者能在本阶段结尾看到「沈栀没有拒绝主角的一次顺手帮忙」]
- 证据线索：动作「没有躲开」/ 台词「……也行吧」
- 若到第8章仍一致拒绝 → 本段判定未达成，禁止进入阶段2
```

### 4D.4 角色线如何规划

```markdown
# 角色线：沈栀
## 阶段（契约式）
| 阶段 | 章节 | 角色变化（from→to） | 验收信号（可grep） | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 1-8 | 戒备→微暖 | 「……也行吧」「没有躲开」 | done |
| 2 | 9-30 | 微暖→依赖 | 第一次主动开口求助 | active |
| 3 | 31-60 | 依赖→信任 | 主动把秘密告诉主角 | planned |
## 审计结果（每卷回填，由闸门写入）
- V1：阶段1达成（证据存在）；阶段2略滞后1次，已在下卷细纲补一个事件
```

### 4D.5 接入 oh-story

- 增量落点：给现有 `chapter-extractor`/`narrative-writer` 写后流程加「记账请求」；`consistency-checker` 增加 `arc-audit` 模式；`story-review` 的 rubric 增加「弧线合规」维度。全部复用现有脚本与 agent 框架，是四方案里**最小 MV**。
- `tracking_commit` 的 JSON 增加 `arc_progress` 字段（每角色 `{current_stage, last_change_chapter, next_due}`）。

### 4D.6 优缺点

- 优点：①把「人设不崩/弧线推进」变成**可自动 gate**（像 CI 一样拦住坏产出）；②与 oh-story 现有 agent 体系（character-designer / consistency-checker / chapter-extractor / story-review）完全对齐，可增量落地、可度量；③验收信号让「变化」显式化，防扁平也防崩。
- 缺点：①依赖多 agent 环境（无 agent 时降级 solo，靠主会话跑检查）；②验收信号写太死会扼杀即兴发挥——建议「验收」指向**可观察事件/行为**而非逐字台词；③记账增加每次写后的处理步骤（时间成本）。

## 5. 四方案横向对比与选型建议

| 方案 | 中心 | 治什么 | 主要成本 | 与 oh-story 兼容度 | 适合 |
| --- | --- | --- | --- | --- | --- |
| A 弧线文件+状态机 | 线 | 单线节奏不可视、阶段推进无约束 | 低（纯 md+脚本） | ★★★★★（微调现有卡） | 现在就可以做；所有长篇 |
| B 事实库+图谱 | 数据 | 渐变证据、跨线审计、规模 | 高（schema/DB/工具） | ★★★☆（追踪层重写） | 50万字+/多势力/严格连载 |
| C 触发式记忆 | 上下文 | 成本与遗忘、配角回归 | 低（改造注入+摘要） | ★★★★☆（升级上下文卡） | 追求 token/成本比，会话式写作 |
| D 记账+审计闸门 | 流程 | 说了不算写了才算、一致性 gate | 中（agent 扩展） | ★★★★★（增量接 agent） | 多 agent 环境、正式连载稳定产出 |

**组合建议（本仓库优先路径）**：

1. **第一步（本周可做）：A + D 的轻量版**——建 `大纲/角色线/` + `arc_advance` 推进 + `arc-audit` 检查。成本低、直接化解「当前角色线只是卡里一段计划」的最大短板（线的可视化 + 自动推进 + 审计）。
2. **第二步（视题材与字数）：C**——上下文卡升级为「分角色近况卡」，降低长文成本、解决配角回归。
3. **第三步（规模化时）：B**——把事实库落进 SQLite，让「弧线视图/关系时间线/全谱审计」成为常驻能力（对接 `story-explorer` 的查询类型）。

## 6. 无论选哪个方案都成立的「角色规划八条」（给 AI 写作的直接提示）

1. **静态/动态分开**：卡里只放“不会错的事实 + 计划”；一切当前值放动态层。AI 混淆两者是头号崩源。
2. **先骨后肉**：开书先定每人的「从哪到哪」（Lie→Truth / 起点姿态→终点姿态 + 弧线类型），再拆阶段；阶段尽量对齐卷或事件，不硬绑章节号。
3. **每个阶段必须有「变化信号」**：读者能在哪看到「他从 A 变到 B」要有具体可观察事件；没有信号的阶段就是空转（或扁平）。
4. **统一坐标**：所有阶段/状态/证据用 `<卷>/<章>/<段落>` 或 `<章节>+<语句>` 打点，机械可查；证据 = 已完成正文的引用，不是计划。
5. **写后记账、记 delta 不记整包**：每章记「谁变了、哪一维、from→to、证据在哪」；渐变因此可回放、可补救，审计才有对象。
6. **定期审计（每卷/10-20 章）**：对每线/每维做「计划 vs 实际」，查提前量、滞后量、越级、缺证据；再顺手做「设定审计」（时间线/年龄/距离/已披露秘密），防吃书。
7. **注入策略固定**：常驻最小集 + 本节活跃角色全量 + 按需查询，读取量不随章数增长（当前 `context_load` 已做到，加线文件/近况卡时要守住这条）。
8. **一致性双重保障**：机械校验（事实锚点/阶段编号/证据存在性）+ LLM 复查（审查 agent）。前者保下限，后者保「读感」。
